\# Banking Domain Ontology

\#\# Purpose

Establish the canonical semantic model of the banking domain.

This document defines the fundamental entities, relationships, boundaries and structural concepts that exist within banking. It enables AI systems to reason consistently across products, journeys and conversations without relying on product-specific implementations.

This document is the semantic foundation upon which higher-level banking knowledge is built.

\# Domain Principles

The banking domain should always be interpreted using the following principles.

\#\# 1\. Everything Is An Entity

Every banking concept represents an identifiable entity.

Examples include:

\- Customer  
\- Account  
\- Product  
\- Transaction  
\- Service  
\- Instrument  
\- Balance  
\- Charge  
\- Limit

Reasoning should always begin by identifying the entity before interpreting its attributes.

\---

\#\# 2\. Entities Never Exist In Isolation

Every entity participates in one or more relationships.

Example relationships include:

\- owns  
\- belongs to  
\- references  
\- affects  
\- contains  
\- creates  
\- modifies  
\- authorizes  
\- settles

AI should reason through relationships instead of isolated values.

\---

\#\# 3\. Values Do Not Exist Without Context

A monetary amount has no semantic meaning unless its associated entity is known.

For example:

₹50

may represent:

\- balance  
\- penalty  
\- interest  
\- refund  
\- charge  
\- reward  
\- deposit  
\- withdrawal

AI should always resolve the owning entity before interpreting a value.

\---

\#\# 4\. Time Is A Domain Dimension

Every banking entity exists within a temporal context.

Time may represent:

\- current state  
\- historical state  
\- scheduled state  
\- future state

AI should never compare values across different temporal contexts without explicit reasoning.

\---

\#\# 5\. States Are Independent Of Entities

Entities possess states.

States are not entities.

Example:

Transaction

↓

Pending

Completed

Failed

Reversed

The transaction remains the same entity while only its state changes.

\---

\#\# 6\. Relationships Are Directional

Relationships always possess direction.

Examples:

Customer

owns

Account

Account

contains

Balance

Transaction

affects

Balance

Reasoning should preserve relationship direction.

\---

\#\# 7\. Objects Have Identity

Every banking object should possess a distinguishable identity.

Identity may be represented through:

\- account number  
\- reference number  
\- transaction identifier  
\- customer identifier  
\- service request identifier

Identity should never be inferred from monetary values.

\# Core Banking Entities

The ontology recognizes the following entity classes.

| Entity | Purpose |  
|---------|----------|  
| Customer | Actor interacting with banking services. |  
| Account | Financial container maintaining balances and transactions. |  
| Product | Banking offering associated with one or more accounts or services. |  
| Balance | Monetary representation of funds within an account context. |  
| Transaction | Atomic financial event affecting monetary state. |  
| Service | Banking capability performed for a customer. |  
| Instrument | Medium used to initiate or authorize financial activity. |  
| Limit | Constraint governing permissible financial activity. |  
| Charge | Monetary adjustment applied under defined conditions. |  
| Document | Formal record generated by banking operations. |  
| Notification | Informational communication generated from banking events. |

\---

\# Canonical Relationship Types

Every relationship within the banking domain should be represented using one of the following semantic forms.

| Relationship | Meaning |  
|-------------|---------|  
| owns | Entity possesses another entity. |  
| belongs to | Entity exists within another entity. |  
| contains | Entity structurally includes another entity. |  
| references | Entity points to another entity. |  
| affects | Entity changes another entity's state or value. |  
| authorizes | Entity grants permission for another entity. |  
| initiates | Entity begins an event or process. |  
| generates | Entity produces another entity. |  
| settles | Entity finalizes another entity. |  
| restricts | Entity limits another entity's behavior. |

These relationships should remain semantically stable across all banking products.

\---

\# Semantic Constraints

The following constraints apply across the ontology.

\- Every balance belongs to exactly one account context.  
\- Every transaction affects at least one financial object.  
\- Every charge references an originating condition.  
\- Every limit constrains a defined financial activity.  
\- Every document represents an immutable historical record.  
\- Every notification represents an informational outcome rather than financial state.  
\- Every service operates upon one or more banking entities.  
\- Every event changes state but does not redefine entity identity.

These constraints form the basis for downstream reasoning.

\# Entity Composition Model

This section defines the structural composition of banking entities.

Composition describes what an entity fundamentally consists of rather than how it behaves.

Entity composition remains independent of products, customer journeys and business rules.

\---

\# Customer Entity

The customer represents the primary participant interacting with banking services.

A customer may own, access or operate multiple banking relationships.

\#\# Composed Of

\- Identity  
\- Profile  
\- Relationships  
\- Accounts  
\- Products  
\- Preferences  
\- Consents  
\- Authorizations

\#\# May Be Associated With

\- Individual  
\- Joint Holder  
\- Guardian  
\- Nominee  
\- Authorized Representative

Customer roles are contextual and may vary across banking relationships.

\---

\# Account Entity

An account is the primary financial container.

Accounts do not represent products.

Instead, accounts operationalize products by maintaining financial state.

\#\# Composed Of

\- Account Identity  
\- Balance  
\- Transactions  
\- Status  
\- Ownership  
\- Limits  
\- Linked Services

\#\# Relationships

Account

├── contains → Balance

├── records → Transactions

├── belongs to → Customer

├── supports → Services

├── constrained by → Limits

└── associated with → Product

\---

\# Product Entity

A product defines the commercial banking offering.

Products describe capabilities.

Accounts operationalize those capabilities.

\#\# Product May Include

\- One or more Accounts  
\- One or more Services  
\- One or more Limits  
\- One or more Charges  
\- One or more Benefits

Products should never be interpreted as balances or transactions.

\---

\# Balance Entity

A balance represents the monetary state of an account.

Balances never exist independently.

Every balance belongs to exactly one account context.

\#\# Characteristics

\- Monetary  
\- Time-sensitive  
\- Derived  
\- Dynamic

Balances may change without altering account identity.

\---

\# Transaction Entity

Transactions represent atomic financial events.

Transactions modify monetary state.

Transactions do not own balances.

Instead, they influence balances.

\#\# Composed Of

\- Identity  
\- Monetary Value  
\- Direction  
\- Time  
\- Status  
\- Reference  
\- Participants

\#\# Relationships

Transaction

├── affects → Balance

├── initiated by → Participant

├── belongs to → Account

└── produces → Record

\---

\# Service Entity

A banking service performs an operation upon one or more banking entities.

Services do not permanently store financial state.

\#\# Examples Of Generic Services

\- Inquiry  
\- Transfer  
\- Verification  
\- Authorization  
\- Update  
\- Download  
\- Registration

These remain service abstractions rather than customer journeys.

\---

\# Limit Entity

Limits define permissible operating boundaries.

Limits never represent available funds.

Limits constrain financial activity.

\#\# May Constrain

\- Deposit  
\- Withdrawal  
\- Spending  
\- Transfer  
\- Investment  
\- Transactions

Limits should always be interpreted together with the activity they govern.

\---

\# Charge Entity

Charges represent monetary adjustments.

A charge is not inherently positive or negative.

Its interpretation depends upon the originating condition.

\#\# Generic Categories

\- Fee  
\- Penalty  
\- Tax  
\- Interest Adjustment

Product-specific charge classifications belong to lower-level knowledge.

\---

\# Document Entity

Documents represent immutable banking records.

Documents preserve historical information.

They should not be interpreted as live banking state.

\#\# Examples

\- Statement  
\- Certificate  
\- Advice  
\- Receipt  
\- Confirmation

\---

\# Notification Entity

Notifications communicate banking events.

Notifications do not alter banking state.

They communicate outcomes generated elsewhere.

Examples include:

\- Alerts  
\- Reminders  
\- Confirmations  
\- Informational Messages

\---

\# Banking Events

Events represent occurrences within the banking domain.

Events initiate state changes.

Events themselves are not permanent banking objects.

Examples include:

\- Deposit  
\- Withdrawal  
\- Payment  
\- Transfer  
\- Settlement  
\- Maturity  
\- Renewal

\# Banking Semantic Model

This section defines how banking information should be interpreted independent of products, customer journeys or implementation.

Semantic reasoning should always precede conversational reasoning.

\---

\# Temporal Semantics

Every banking entity exists within a temporal context.

Time is a first-class semantic attribute rather than supporting metadata.

Banking information should never be interpreted without considering the associated time dimension.

\---

\#\# Temporal Categories

| Context | Description |  
|----------|-------------|  
| Current | Represents present banking state. |  
| Historical | Represents completed past state. |  
| Scheduled | Represents future planned state. |  
| Processing | Represents state currently changing. |  
| Continuous | Represents state maintained over time. |

AI should never compare values across different temporal categories without explicit reasoning.

\---

\#\# Temporal Independence

Different banking values may belong to different periods simultaneously.

Example:

\- Current account balance  
\- Previous financial year contribution  
\- Future scheduled payment

Temporal proximity should never imply semantic relationship.

\---

\#\# Temporal Integrity

AI should preserve the original time context of every entity.

Do not merge:

\- Current balances  
\- Historical deposits  
\- Previous charges  
\- Future obligations

unless explicitly supported by domain relationships.

\---

\# Monetary Semantics

Money represents a value.

Meaning originates from the owning entity rather than the amount itself.

₹50 has no semantic interpretation until ownership is resolved.

Possible meanings include:

\- Balance  
\- Interest  
\- Charge  
\- Penalty  
\- Refund  
\- Deposit  
\- Withdrawal  
\- Reward

Resolve ownership before reasoning.

\# Identity Semantics

Identity distinguishes entities.

Identity remains persistent even when attributes change.

Examples:

\- Customer Identifier  
\- Account Identifier  
\- Transaction Reference  
\- Service Request Reference  
\- Document Reference

Identity should never be inferred from names, balances or timestamps.

\---

\# Reference Semantics

References establish traceability.

References do not imply ownership.

Example:

references

Transaction

Transaction

references

Account

Account

references

Ownership and reference should never be treated interchangeably.

\---

\# Limit Semantics

Limits represent permissible boundaries.

Limits are constraints.

Limits are not balances.

Limits are not obligations.

Limits exist independently of utilization.

Examples of generic interpretations:

Maximum permissible

Remaining permissible

Consumed permissible

AI should distinguish between:

Limit

Utilization

Remaining Capacity

These represent different semantic concepts.

\---

\# Capacity Semantics

Capacity represents remaining permissible action.

Capacity is derived.

Capacity should never be interpreted as monetary ownership.

Examples include:

\- Available to Deposit  
\- Available Credit  
\- Remaining Transfer Capacity

Capacity depends upon:

Limit

minus

Utilized Amount

Capacity is contextual rather than absolute.

\---

\# Charge Semantics

Charges represent monetary adjustments.

Charge type should always be resolved before reasoning.

Possible categories include:

\- Fee  
\- Penalty  
\- Tax  
\- Interest Adjustment

These categories should never be treated as interchangeable.

\---

\# Event Semantics

Events represent occurrences.

Events change state.

Events do not permanently store information.

Examples:

Deposit

Withdrawal

Transfer

Payment

Settlement

Renewal

Maturity

Event completion may generate:

\- Transaction  
\- Notification  
\- Document

\---

\# Historical Semantics

Historical information preserves completed banking reality.

Historical values should never be recalculated using current state.

Past information remains immutable unless explicitly corrected.

\---

\# Current Semantics

Current information represents latest observable banking state.

Current state may evolve continuously.

Reasoning should always distinguish:

Current

vs

Historical

vs

Scheduled

\---

\# Semantic Consistency Rules

Maintain semantic consistency throughout reasoning.

Never:

Interpret values without ownership.

Infer relationships from proximity.

Merge unrelated temporal contexts.

Substitute similar banking concepts.

Assume equivalent terminology implies equivalent meaning.

\---

\# Semantic Disambiguation

Resolve ambiguity using the following order.

1\. Banking Entity  
2\. Conversation Context  
3\. Product Context  
4\. Temporal Context  
5\. Relationship Graph  
6\. Customer Intent

Clarification should only occur when ambiguity cannot be resolved through semantic reasoning.

AI may infer only when supported by semantic relationships.

Not permitted:

Current balance equals ₹50,000.

Inference requires explicit supporting relationships.

\# Ontology Constraints

The ontology guarantees:

\- One entity may have multiple relationships.  
\- One relationship may connect multiple entities.  
\- Entity identity persists across state changes.  
\- Monetary values derive meaning from ownership.  
\- Time modifies interpretation without redefining identity.  
\- References preserve traceability.  
\- Historical information remains semantically independent from current state.

These guarantees apply across all banking products.
